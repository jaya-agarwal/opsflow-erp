# OpsFlow — ERP & CRM Operations Portal

OpsFlow is a production-minded Mini ERP + CRM for a wholesale/distribution workflow. It covers the required case-study modules and adds an operations intelligence layer so the demo feels like an internal product rather than a generic CRUD dashboard.

## What makes this version distinctive

- **Operations Readiness Score** — a transparent control score built from low-stock items, overdue follow-ups and draft challans.
- **Exception Radar** — prioritizes a handful of operational signals and links each signal to the right workflow.
- **Stock Guard** — confirmed challans re-check stock inside a PostgreSQL transaction with row-level locking before an OUT movement is committed.
- **Immutable product snapshots** — historical challan lines preserve product name, SKU, price and quantity at transaction time.
- **CRM follow-up timeline** — customer interactions become an auditable handoff trail instead of a single notes field.
- **Audit Trail** — important actions are traceable by actor, entity, action and metadata.
- **Invoice Center** — Accounts can continue from confirmed challans to linked invoices.
- **A4 PDF documents** — challan and invoice PDFs are generated by the API.
- **Command palette** — `Ctrl/Cmd + K` for fast navigation.
- **Motion system** — route transitions, reveal animations, hover states and responsive drawer transitions are used with restraint.

## Local setup WITHOUT Docker (recommended for this submission)

**Current machine status:** Docker Desktop is not currently running because Windows has reported that virtualization support is not detected. This is intentionally documented here. The required application workflow does **not** depend on Docker, so continue with Node.js + Neon. Docker files are included only as the optional bonus path.

**Docker is optional for this case study.** The current local setup uses Node.js + Neon PostgreSQL, so Docker does not need to be running for the application, the screen recording, or the Vercel/Render deployment flow.

Requirements:
- Node.js 22+
- npm 10+
- A PostgreSQL database. Neon is recommended.

### 1. Install dependencies

```powershell
npm install
```

### 2. Create the root `.env`

Keep `.env.example` as the safe template. Create **`.env` in the project root** (next to `package.json`) and add your private Neon connection string.

```env
PORT=5000
DATABASE_URL=postgresql://USER:PASSWORD@HOST/DBNAME?sslmode=require
JWT_SECRET=replace-with-a-long-random-secret
CORS_ORIGIN=http://localhost:5173
NODE_ENV=development
```

Never commit `.env`.

### 3. Initialize and seed

```powershell
npm run db:init
npm run seed
```

`db:init` applies `database/schema.sql`; `seed` inserts the four demo roles and realistic sample records.

### 4. Start

```powershell
npm run dev
```

Open `http://localhost:5173`. API health check: `http://localhost:5000/health`.

## Deployment (recommended: Vercel + Render + Neon)

The assignment explicitly permits Vercel-like frontend hosting, Render-like backend hosting, and Neon/Supabase/Render Postgres. AWS is optional.

### Backend on Render

1. Push this repository to GitHub.
2. Create a Render Web Service from the repository.
3. Build command: `npm install && npm run build -w apps/api`
4. Start command: `node apps/api/dist/server.js`
5. Add `DATABASE_URL`, `JWT_SECRET`, `CORS_ORIGIN`, and `NODE_ENV=production`.
6. Set `CORS_ORIGIN` to the final Vercel URL.
7. Use `/health` as the health check.

`render.yaml` is included as a deployment starting point.

### Frontend on Vercel

1. Import the GitHub repository.
2. Set the project Root Directory to `apps/web`.
3. Keep the Vite build settings or use `npm run build` with output `dist`.
4. Add `VITE_API_URL=https://YOUR-RENDER-API.onrender.com/api`.
5. Redeploy after the environment variable is added.

`apps/web/vercel.json` handles SPA fallback routing.

## Production readiness checklist

- Keep production secrets only in platform environment variables.
- Use a strong `JWT_SECRET`.
- Keep `CORS_ORIGIN` restricted to the deployed frontend domain.
- Use HTTPS at the hosting platform.
- Keep database credentials out of Git.
- Run the Postman smoke tests after deployment.
- Verify `/health` before recording the final demo.
- Test the negative-stock path and confirm the database remains unchanged on rejection.
